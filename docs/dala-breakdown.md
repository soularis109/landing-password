# Як зроблено dala.craftedbygc.com: розбір

Розбір зроблено за публічними бандлами сайту (`/scripts/theme.js`, `/scripts/vendor.js`).
Їхнього коду тут немає: лише опис механізмів моїми словами та власний псевдокод.
Для кожного розділу вказано, як те саме зроблено в нашому демо.

---

## 0. Головне за 30 секунд

| Що бачиш | Як це насправді зроблено |
|---|---|
| Велика піраміда | **Не одна модель.** Це ~10 000 маленьких пірамідок (7 000 на мобільних), кожна окремим інстансом |
| Піраміда розсипається, збирається, перетікає в інші форми | **GPU-симуляція пружин** (GPGPU): позиції і швидкості частинок лежать у текстурах і щокадру рахуються шейдером |
| Хвиля, що прокочується формою при морфінгу | Кожна частинка має свій «порядковий номер» за напрямком (зверху вниз, зліва направо…), тож перехід стартує з невеликою затримкою на номер |
| Камера / форма рухаються зі скролом | **Не ScrollTrigger-таймлайн**, а одне число `sectionProgress` (номер секції + дробова частина) і функції «перетворити діапазон» + clamp, з lerp |
| Плавний скрол | Власний smooth-scroll (не Lenis): wheel → targetPos, currentPos доганяє з lerp ≈ 0.075 |
| Розмиття, світіння | EffectComposer: RenderPass ×2 → **UnrealBloom** → **BokehPass** (лише десктоп) → Vignette |
| Поява тексту | GSAP + ScrollTrigger (`once: true`) через data-атрибути `animate-from` / `animate-to` |
| Зерно / «туман» поверх сцени | Окремий напівпрозорий шар у 3D з текстурою шуму перед камерою |

## 1. Архітектура

У них невеликий власний «рушій», а не React:

- **Один глобальний RAF-список** (`RAFCollection`). Кожен модуль реєструє свій `onRaf` з **пріоритетом**:
  спочатку рахується скрол, потім DOM→WebGL-синхронізація, останнім (пріоритет 99) рендериться WebGL.
  Порядок гарантує, що 3D у кадрі бачить уже оновлену позицію скролу.
- **Подієва шина** (`emit/on`): `resize`, `pointermove`, `section:enter`, прогрес прелоадера.
- **Глобальний об'єкт стану** (`u.*`): `isMobile`, `window.w/h`, `sectionIndex`, `sectionProgress`, посилання на WebGL.

> **У нас:** ту саму роль грає `gsap.ticker` у `components/Scene.tsx`: Lenis → ScrollTrigger → `experience.update()`
> в одному тіку. Глобальний стан у нас локалізований в `SceneState` (`lib/webgl/state.ts`).
> **Варто перейняти:** явний порядок оновлень у кадрі. Коли модулів багато, це рятує від «тремтіння» на 1 кадр.

## 2. Прелоадер

- `AssetLoader` збирає масив промісів: шрифти, `<img>` без lazy, відео, текстури (PNG/JPG/EXR/KTX2), моделі GLB (з DRACO).
- Кожен виконаний проміс шле подію з `percent = виконано / всього * 100`. Лічильник «0 Completed» слухає саме її.
- Тяжкі задачі (парсинг GLB) ставляться в **TaskScheduler**, чергу, яка виконує по одній задачі, щоб головний потік не «зависав».
- Після завантаження: зчитування позицій частинок із текстури (див. §4), збирання матеріалів, `onEnterSite()`:
  шар-«туман» зникає, частинки активуються.

> **У нас:** `lib/loader.ts`: та сама ідея (проміси → відсоток), плюс плавне доганяння числа і мінімальна тривалість.
> **Варто перейняти:** чергу для важких задач, якщо моделей багато.

## 3. Сцена і камери

- **Дві сцени, дві камери**:
  1. «частинкова» сцена: перспективна камера з малим fov, у ній піраміди, шар туману, передні частинки;
  2. «DOM-сцена»: камера на z = 2000 з fov, підібраним так, що **1 одиниця = 1 CSS-піксель**. Туди можна
     проєктувати HTML-елементи (`dom2webgl`), щоб WebGL-об'єкти стояли точно поверх розмітки.
- Паралакс миші: **обертання камери** (не позиції) на кілька сотих радіана, з lerp 0.1.
- `pixelRatio`: 1 на десктопі (!), 2 на мобільних. Важкий пост-процесинг на retina-моніторі коштував би вчетверо дорожче.

> **У нас:** одна сцена; паралакс обертає `rig` навколо камери (`lib/mouse.ts` + `Experience.update`).
> **Варто перейняти:** pixelRatio 1 на десктопі з важкими ефектами; трюк «1 unit = 1px» для синхронізації з DOM.

## 4. Серце: 10 000 частинок на GPU

### 4.1 Звідки беруться форми
Цільові позиції частинок **«запечені» в EXR-текстуру** (float-текстура, 200×200, розбита на 4 квадранти 100×100).
Кожен квадрант містить одну форму, тобто 10 000 точок (x, y, z закодовано в RGB):

```
[ форма A | форма B ]
[ форма C | форма D ]
```

Піраміда та її «перетворення» по секціях — це просто 4 хмари точок. Їх, найімовірніше, згенерували в
Houdini/Blender і експортували як текстуру.

### 4.2 Порядок частинок (той самий «хвильовий» ефект)
Після завантаження CPU один раз зчитує текстуру позицій і **для кожної форми сортує частинки за напрямком**
(за Y згори вниз, за X зліва направо тощо). Номер у відсортованому списку стає параметром частинки.
Перехід A→B тоді виглядає як «прокочування» хвилі через форму, а не як одночасний морфінг.

### 4.3 Симуляція (ping-pong FBO)
Дві пари render target'ів: **швидкість** і **позиція**. Щокадру:

```
// мій псевдокод, не їхній
target   = mix(formaA, formaB, stagger(progress, order))   // куди частинка «хоче»
accel    = (target - position) * spring                    // пружина
velocity = (velocity + accel) * friction                   // затухання
position = position + velocity
```

`stagger(progress, order)` = `clamp(progress * (1 + d*(N-1)) - d*order, 0, 1)`: стандартна формула
«затримка на індекс», яка розтягує загальний прогрес 0…1 так, що остання частинка стартує пізніше за першу.

Чому пружина, а не просто `mix`: коли ціль різко змінюється (скрол, «вибух», миша), частинки
**перелітають і пружинять**. Від цього рух здається живим. Жорсткість пружини в кожної частинки трохи різна.

### 4.4 Рендер частинок
- Геометрія однієї пірамідки береться з GLB. Ціль LOD-версій (`py-lod1…7`) — мати дешевшу сітку для дальніх або дрібних.
- Матеріал: стандартний three.js-матеріал, розширений через **`onBeforeCompile`**: у вершинний шейдер
  вставляються uniform'и і код, який читає позицію з текстури симуляції за `instanceId`, додає обертання,
  масштаб, вплив миші.
- Колір береться з **градієнтної текстури-палітри** (`cd-33.png`), розмір — з окремої текстури масштабів.

> **У нас:** `lib/webgl/Pyramid.ts`: 160 інстансів, позиції рахує CPU в `update()`. Для 160 це нормально,
> для 10 000 вже ні.
> **Як підтягнути демо до їхнього рівня:** `GPUComputationRenderer` з `three/examples/jsm/misc/`
> (готовий ping-pong) + `onBeforeCompile` для читання позицій у вершинному шейдері.

## 5. Скрол → анімація

### 5.1 Smooth-scroll
Власна реалізація: слухає `wheel`, накопичує `targetPos`, щокадру `currentPos += (target - current) * 0.075`,
контент рухається `transform`-ом. Підтримує **горизонтальний режим** (`isHorizontal`), тому скрізь
перевіряється вісь.

### 5.2 `sectionProgress`: одне число на всю сторінку
Кожна `<section>` при вході у в'юпорт стає «поточною». У RAF рахується:

```
sectionProgress = індексСекції + |скрол - верхСекції| / висотаСекції
```

Наприклад, 2.35 означає «35% третьої секції». Усі 3D-параметри задано як **сума шматочків**:

```
// мій псевдокод
x = clamp(remap(p, 0.0, 1.0,  3.0, -4.5)) +   // секція 0: їде ліворуч
    clamp(remap(p, 1.25, 1.5, 0.0,  4.1)) -   // секція 1: повертається
    ...
current += (x - current) * 0.1               // lerp замість scrub
```

Кожен рядок — це «на ділянці скролу [a, b] змінити параметр від c до d». Параметри: позиція, обертання,
радіус форми, «вибух», прогрес морфінгу між 4 формами.

**Чому не GSAP-таймлайн?** Значення подаються одразу у кілька місць (матеріал, depth-матеріал,
обидва симуляційні шейдери), а lerp на кожному дає ту саму інерцію, що й `scrub`. Мінус: такий код
важко читати і правити.

> **У нас:** `lib/scroll/timeline.ts`: один master-timeline зі `scrub: 1.2` і кадрами на секцію.
> Результат той самий (прогрес скролу → параметри з інерцією), але читабельніший.
> **Варто перейняти:** нічого не міняти. Наш підхід еквівалентний і простіший у підтримці.

### 5.3 Reveal-анімації DOM
Декларативно через атрибути: `animate-from="..."` / `animate-to="..."` / `animate-mq="..."` на елементі.
Скрипт збирає їх у GSAP-твіни з `ScrollTrigger({ once: true })`, ease переважно `expo.out`.
На resize ще не запущені твіни перебудовуються. Є навіть «дзеркалення» властивостей на WebGL-об'єкти (`x → position.x`).

> **У нас:** `data-reveal="lines|fade"` + `createReveals()`. Та сама ідея, менше можливостей.
> **Варто перейняти:** атрибут медіа-запиту (`animate-mq`), щоб вимикати окремі анімації на мобільних.

## 6. Пост-обробка

Ланцюжок EffectComposer:

1. **RenderPass**: частинкова сцена;
2. **RenderPass**: DOM-сцена поверх (`clear = false`, очищення лише глибини);
3. **UnrealBloomPass**: м'яке світіння (низький threshold ≈ 0.16, strength ≈ 0.4);
4. **BokehPass**: «кінематографічний» DOF (варіант відомого шейдера з кільцевою вибіркою: rings/samples,
   focalDepth, fstop), **лише на десктопі**;
5. **VignettePass**: сильна віньєтка.

Плюс текстура `dof-2k` як спрайт для форми боке і `noise.jpg` для зерна.

> **У нас:** `lib/webgl/BokehPass.ts`: власний DOF із золотою спіраллю + зерно + віньєтка в одному проході;
> bloom немає.
> **Варто перейняти:** додати `UnrealBloomPass` перед bokeh. Він дає те саме «сяйво» граней.

## 7. Продуктивність: що вони роблять

- Менше частинок і без bokeh на мобільних, окрема мобільна модель і окремі криві руху.
- Стиснуті ресурси: **DRACO** для геометрії, **KTX2/Basis** для текстур.
- `renderer.initTexture()` одразу після завантаження: текстура заливається на GPU під час прелоадера, а не в першому кадрі.
- `antialias: false`, `stencil: false`, pixelRatio 1 на десктопі.
- Важкі задачі завантаження йдуть через чергу.

## 8. Розбір блоків сторінки

Дані зібрано з DOM запущеної сторінки: секції, data-атрибути анімацій, WebGL-компоненти.

### 8.1 Як анімації описані в розмітці
Анімації не захардкожені в JS, а задані **атрибутами в HTML**:

- `animate-from="..."`: параметри `gsap.from()` (або назва пресету) прямо в розмітці;
- `animate-to="..."`: те саме для `gsap.to()`;
- `animate-mq="sm" | "smMax"`: анімація створюється лише при певному медіа-запиті;
- `dom2webgl="c:Pyramid"`: на місці DOM-елемента рендериться WebGL-компонент.

Один скрипт при завантаженні знаходить ці атрибути, розбирає їх і створює GSAP-твіни.
За замовчуванням додається ScrollTrigger з `once: true` (запуск один раз, коли елемент входить у в'юпорт).
Дизайнер чи верстальник може міняти анімацію, не торкаючись JS.

### 8.2 Головний текстовий ефект: `splitTextRotateIn`
Це зареєстрований GSAP-ефект (`gsap.registerEffect`), який використовується майже на всіх заголовках і абзацах:

1. GSAP SplitText ділить елемент (або його дочірні `p`, якщо задано `children`) на **рядки**.
2. Кожен рядок стає маскою (`overflow: hidden`), а його вміст переноситься у вкладений `div`.
3. Вкладені `div` анімуються з-під маски: знизу вгору з невеликим **поворотом** (близько 7°), ease `expo.out`.

Поворот — ключова деталь: рядки виїжджають не рівно, а «з розгону», тому ефект виглядає дорожче, ніж звичайний slide-up.

> **У нас:** `lib/scroll/splitLines.ts` + `createReveals()` роблять кроки 1–3 без повороту.
> Щоб отримати їхній вигляд, достатньо додати `rotate` до `from`-твіну і `transform-origin: left top` на `.line`.

### 8.3 Секції

| Блок | Висота | Що анімується |
|---|---|---|
| **Landing** (hero) | 1 екран | Заголовок через `splitTextRotateIn` одразу після прелоадера; підзаголовок і текст із затримкою 1 с; кнопки виїжджають знизу (`yPercent`, невеликий поворот, затримка 1.5 с). На фоні частинки збираються в піраміду |
| **Introduction** | — | Заголовок і текст з тим самим ефектом; старт, коли верх блоку торкається низу екрана (`start: 'top bottom'`), тобто раніше за типові `top 80%` |
| **Manifesto** (3 підсекції) | ~1.5 екрана кожна | Абзаци по рядках. Для мобільних і десктопа **різні контейнери** тексту, перемикаються через `animate-mq`. Саме тут працює `sectionProgress`: частинки морфляться між формами, поки ти скролиш високі секції |
| **Team** | ~2 екрани | Шапка зі **scrub-паралаксом** (зсув на кілька vw, `scrub: 0.5`, `once: false`, тобто прив'язана до скролу в обидва боки). Біля фото людей стоять **5 WebGL-пірамід** (`c:Pyramid`), позиціоновані за DOM через `dom2webgl`. Іконки інвесторів з'являються знизу з поворотом ~14° |
| **CTA / footer** | — | Заголовок із `splitTextRotateIn` |

### 8.4 Висновки для свого проєкту
- **Декларативні анімації в атрибутах** зручні на великих сайтах і в CMS. На маленькому лендінгу простіше конфіг у JS, як у нас.
- **Високі секції (150 vh)** дають 3D-сцені «час» на перехід. Без них морфінг пролітає за секунду.
- **`once: true` для тексту + `scrub` для 3D і паралаксу**: усталена комбінація. Текст не «відкочується» при скролі вгору, а сцена завжди відповідає позиції скролу.
- **DOM → WebGL** (`dom2webgl`): верстка лишається звичайною, а WebGL-об'єкт стоїть точно на місці div-плейсхолдера. Наступний крок, якщо захочеш 3D-елементи всередині контентних блоків.

## 9. План, як довести наше демо до їхнього рівня

1. `GPUComputationRenderer`: позиція + швидкість, пружина/тертя (§4.3).
2. Генератор форм: семплювання точок на поверхні 2–4 мешів (`MeshSurfaceSampler` з three/examples) → DataTexture.
3. Сортування частинок за напрямком і stagger-формула (§4.2).
4. `onBeforeCompile` на `MeshPhysicalMaterial` / `MeshStandardMaterial` для `InstancedMesh`.
5. Прогрес морфінгу і «вибух» у `SceneState`, керовані тим самим scroll-timeline.
6. `UnrealBloomPass` перед bokeh.
